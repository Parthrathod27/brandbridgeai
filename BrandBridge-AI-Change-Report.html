2Critical bug found and fixed

Escaped template literals in the brand profile form

src/components/dashboard/brand/BrandProfileForm.tsx

Seventeen JSX template literals in this file had their interpolation escaped — \${ instead of ${. JavaScript therefore treated the entire expression as literal text rather than evaluating it, and that raw text was passed straight into the className and style attributes.

// Before — the backslash disables interpolation entirely
className={`... transition-all duration-300 \${activeTab === 'basic' ? 'block' : 'hidden sm:hidden'}`}

// After
className={`... transition-all duration-300 ${activeTab === 'basic' ? 'block' : 'hidden sm:hidden'}`}

The practical effect was that several interactive parts of the brand profile page did nothing at all:

Broken behaviourSymptom before the fix
Mobile accordion sectionsSections never expanded or collapsed on tap — the show/hide class was never computed
Desktop tab highlightingActive tab never received its underline or accent colour
Profile completeness barWidth was the literal string, so the bar never reflected the real percentage
Registered-business toggleSwitch never moved or changed colour when toggled
Availability status dotColour never matched the selected status
Floating save barNever slid into view when the form became dirty

Secondary fix in the same file

The floating save bar offset the sidebar with md:pl-[17rem], but the sidebar only becomes a static column at the lg breakpoint. Between 768 px and 1024 px the bar was indented for a sidebar that was not there. Changed to lg:pl-[17rem].

Why this matters most This was not a styling preference — it was broken code that TypeScript cannot catch, because an escaped template literal is still a perfectly valid string. It would not have surfaced in a build or a type check.

3Mobile responsiveness

The application already had a solid responsive foundation — the sidebar drawer, the two-pane messages flow, and horizontally scrolling tab strips were all in place. The work below closes the gaps that remained.

3.1  iOS auto-zoom on form focus

src/styles/brandbridge.css

Safari on iOS zooms the whole page whenever a focused input has a font size below 16 px. Every field in the app used 0.875rem (14 px), so tapping any input jumped the layout and the user had to pinch back out. Form controls are now pinned to 16 px on screens up to 640 px.

/* iOS Safari zooms the viewport when a focused field is under 16px.
   Keep every form control at 16px on phones so focus never zooms. */
@media (max-width: 640px) {
  .bb-input, input.bb-input, select.bb-input, textarea.bb-input,
  input:not([type="checkbox"]):not([type="radio"]):not([type="range"]),
  select, textarea { font-size: 16px; }
}

3.2  Viewport height units in modals

Sixteen components sized themselves with vh. On mobile browsers vh is measured against the viewport including the collapsible address bar, so modal content and action buttons were pushed below the visible area. All were converted to dvh, which tracks the actual visible height.

3.3  Hover-only controls unreachable on touch

src/components/messages/ChatWindow.tsx

The edit and unsend buttons on your own messages were opacity-0 group-hover:opacity-100. Touch devices have no hover state, so on a phone these controls could never be revealed — the features were effectively absent on mobile. They are now visible by default and only hover-gated from sm upward, preserving the clean desktop appearance.

4Features added

4.1  Error, loading and 404 boundaries New

The application previously had no error.tsx, loading.tsx or not-found.tsx anywhere. A failed API call or a thrown render produced either a blank white screen or an unhandled React crash, with no way back other than the browser's back button. Six files now cover every failure path:

FileCatches
src/app/error.tsxAny uncaught render or data error, with a retry button and a route back to the dashboard
src/app/global-error.tsxFailures in the root layout itself. Renders its own <html> shell with inline styles, since neither the theme provider nor Tailwind is available at that point
src/app/not-found.tsxUnmatched routes — a branded 404 rather than the Next.js default
src/app/loading.tsxTop-level route transitions
src/app/(protected)/loading.tsxDashboard navigation, using a skeleton shaped like the real dashboard (header, stat row, content cards) so the layout does not jump when data lands
src/app/(protected)/error.tsxDashboard section failures. Renders inside the shell, so the sidebar and header stay usable and the user is not ejected from the app

Where Next.js supplies an error digest, it is displayed so a user can quote it in a support request and you can match it to your server logs.

4.2  Live messaging New

src/components/messages/ChatWindow.tsx · MessagesCenter.tsx

Chat previously fetched messages only when you switched conversation or sent something. A message from the other participant never appeared — the recipient had to reload the page to discover it, which made the messaging feature effectively unusable for real conversation.

Messages now poll every 5 seconds and the conversation list every 15 seconds. Four details make this safe rather than merely functional:

  • No spinner flash. Background polls run in a silent mode that never touches the loading state, so the UI does not flicker every five seconds.
  • No pointless re-renders. Each poll is structurally compared against the current list; if nothing changed, React state is left untouched.
  • Scroll position is respected. The view auto-scrolls only when new messages arrive and you are already near the bottom. Someone reading back through history is never yanked away.
  • Paused in background tabs. Polling stops while the tab is hidden and fires an immediate catch-up fetch on return, so a backgrounded tab costs nothing.

The conversation-list refresh additionally preserves any unsent draft conversation and never steals the selection you are currently viewing.

4.3  Rate limiting on AI endpoints Hardening

src/lib/rate-limit.ts — applied to all 9 routes under src/app/api/ai/

Every Gemini-backed route was authenticated but otherwise unlimited: any logged-in account could issue unbounded paid API calls. Two budgets now apply per user:

BudgetLimitPurpose
Per route12 / minuteStops one endpoint being hammered
Across all AI routes30 / minuteStops the nine routes being summed to bypass the per-route cap

Exhausting either returns HTTP 429 with a Retry-After header and standard X-RateLimit-* headers, plus a plain-language message the UI can display directly.

Deployment caveat — read before going to production Counters are held in process memory. On a single long-lived server that is exactly right: no extra infrastructure, no network hop. On Vercel or any horizontally scaled deployment, each instance keeps its own counters, so the real ceiling becomes limit × instances. Every call routes through a single hit() function specifically so this can be swapped for a Redis INCR/EXPIRE in one place when you scale out.

4.4  Image loading New

27 raw <img> tags across 18 files now carry loading="lazy" and decoding="async", so off-screen avatars, logos and portfolio thumbnails no longer block initial render or compete for bandwidth on a mobile connection.

A full migration to next/image was deliberately not done — see Section 7.

5.7  AI rate limiting

Log in, open DevTools → Console on any page of the app, and paste:

for (let i = 1; i <= 15; i++) {
  const r = await fetch('/api/ai/hub', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ type: 'consultant', prompt: 'test' })

  console.log(i, r.status, r.headers.get('X-RateLimit-Remaining'));

Expect the first 12 to return 200 with a decreasing remaining count, then 429 from the 13th onward. Wait 60 seconds and confirm requests succeed again. To confirm the global ceiling, repeat while alternating across several different /api/ai/* routes — you should be cut off at 30 requests in the minute even though no single route reached 12.

7Limits and recommended next steps

What was deliberately not done

ItemReason
Full next/image migration Uploads take two different shapes. When Cloudinary credentials are set, images are Cloudinary URLs, which next/image handles and which are already allow-listed in next.config.ts. When those credentials are absent the upload route falls back to inline base64 data: URLs, which next/image cannot optimise and would need unoptimized to render at all. Migrating blindly risked breaking image display in exactly the fallback path. Lazy loading was applied instead, which is safe for both shapes.
Real-time transport (SSE or WebSocket) Polling was chosen because it required no infrastructure change and closed the functional gap immediately. It is the right first step, not the final answer — see below.
Distributed rate limiting Would require Redis or Upstash, which is an infrastructure decision that is yours to make. The code is structured so the swap is a single function.
Component and end-to-end tests The 58 tests cover pure logic. Component tests are wired and ready — @testing-library/react and jsdom are installed and the config supports a per-file jsdom docblock — but no component suites were written in this pass.

Recommended next, in order

  1. Replace chat polling with Server-Sent Events. At 5-second polling, 100 concurrent users generate roughly 72,000 requests an hour against MongoDB. SSE reduces that to one open connection each and delivers messages instantly.
  2. Move rate-limit counters to Redis before any multi-instance deployment, otherwise the ceiling scales with your instance count.
  3. Add response caching to the AI routes. Rate limiting caps abuse but identical prompts still cost a full Gemini call every time.
  4. Write component tests for the brand profile form. It is the most complex stateful form in the app and it is where this pass found a bug that no type check could catch.
  5. Verify on real iOS hardware. The zoom-on-focus fix in 3.1 cannot be reproduced in desktop device emulation.
